# 代码开发 Skill（coding-skill）

## 目标

用现有的 ReAct Agent 和 Tool 系统完成代码开发类任务：先把代码读明白，再定位问题，最小化修改，最后用测试或命令验证，并给出可审计的结论。

## 使用场景

- 阅读和分析代码：解释某段逻辑、梳理模块调用链、回答“这段代码在做什么”。
- 定位 Bug：排查报错、异常行为、逻辑错误，找到根因并修复。
- 修改代码：修复缺陷、新增/调整功能、重构局部代码、编写脚本。
- 运行测试与验证：跑现有测试、做语法检查、验证改动前后行为。

## 执行环境约定

- 所有工具都以 `backend/` 为项目根目录：
  - `read_file` 的相对路径基于 backend（例如 `graph/agent.py`）。
  - `write_file`、`edit_file` 的相对路径同样基于 backend，并且不允许越出 backend。
  - `terminal` 的当前工作目录是 backend。
  - `python_repl` 的执行目录是 backend。
- 访问仓库根目录文件（如 `README.md`）时，路径写成 `../README.md`。
- 路径统一使用正斜杠 `/`。
- 当前环境为 Windows，`terminal` 默认执行 PowerShell 命令；不要依赖 bash 专有语法。

## 工作流程

### 1. 理解需求，锁定范围

1. 明确任务类型：解释分析 / 定位 Bug / 修改功能 / 运行验证。
2. 确认涉及的文件或模块；范围模糊时先做一次快速文件勘察，不要凭空假设。
3. 动手前先想清楚“完成标准”，避免改到一半才发现方向不对。

### 2. 阅读和分析代码

1. 用 `read_file` 精读目标文件；单次最多返回 10000 字符，大文件先用 terminal 定位再分段读取。
2. 用 `terminal` 做关键字和文件定位：
   - 优先 `rg`（如 `rg "函数名" -n`、`rg --files`）。
   - 没有 `rg` 时用 PowerShell：`Get-ChildItem -Recurse -File | Select-String "关键字"`。
3. 先读入口和主流程，再沿调用链向下，关注函数签名、返回值、异常处理、外部依赖。
4. 建立“问题 → 相关代码位置”的映射后再进入下一步。

### 3. 定位 Bug / 问题根因

1. 先复现：能复现的问题才有确定的根因；不能复现时，明确说明缺少哪些复现条件。
2. 缩小范围：用最小输入、单一函数或二分法隔离问题，写最小复现片段。
3. 用 `python_repl` 跑短代码验证假设；用 `terminal` 跑真实命令观察实际报错。
4. 区分“症状”和“根因”，未确认根因前不要改代码。
5. 优先排查常见问题：路径/编码、空值、类型、边界条件、环境变量、依赖版本、权限。

### 4. 修改代码

1. 改已有文件时优先用 `edit_file` 做精确替换：`old_text` 必须从 `read_file` 结果逐字复制，并带上足够上下文保证唯一；多处匹配时明确用 `replace_all=true`。
2. 新建文件或整文件重写时用 `write_file`；覆盖已有文件必须显式传 `overwrite=true`，不要靠 terminal 重定向绕过确认。
3. 小步修改：一次只改一个逻辑点，改完立即验证。
4. 遵循项目现有风格：与相邻代码保持一致的命名、缩进、注释语言和结构。
5. 只改与任务相关的文件，不重排、不重构无关代码，不删除用户已有功能。
6. 修改后复查改动内容，确认没有误改其他逻辑。

### 5. 运行测试与验证

1. 语法检查：
   - Python：`python -m py_compile <文件>`
   - Node/JS：`node --check <文件>`
2. 单元测试：项目有 pytest 时优先 `python -m pytest <相关测试文件> -q`；没有测试时至少运行受影响模块的现有命令。
3. 回归验证：改动涉及已有功能时，运行相关测试并对比改动前后输出。
4. 每个验证步骤记录结果（通过/失败/关键输出），失败信息作为下一步依据，不要隐瞒。

### 6. 汇报结果

结论先行：改了什么、为什么改、验证结果如何。列出涉及的文件路径、关键改动点、测试命令与结果；未完成或有风险的事项要明确说明。

## 工具使用约定

- `read_file`：精读单个文件；大文件配合 terminal 定位后分段读取。
- `write_file`：新建文件或整文件重写；默认 `overwrite=false`，已有文件不会被静默覆盖。
- `edit_file`：对已有文件做精确文本替换，适合最小化改动；找不到 `old_text` 或匹配不唯一时会明确报错。
- `terminal`：运行构建、测试、搜索、文件操作；cwd 为 backend，输出截断到 5000 字符，超时 30 秒。
- `python_repl`：跑短 Python 片段验证假设、解析输出、做计算；超时 15 秒。
- `fetch_url`：只用于需要抓取外部文档/链接的场景，不用于本地代码。
- `add_longterm_memory`：仅当出现值得跨任务复用的经验或用户偏好时才写入，不要记录一次性任务细节。

## 注意事项

- 不要执行危险命令（如 `rm -rf /`、关机、格式化等）；工具本身有黑名单，也不要去尝试绕过。
- `write_file`、`edit_file` 不能改动 `.git`、`.venv`、`node_modules`、`__pycache__` 等目录和 `.env`，被拦截时不要试图改用 terminal 绕过。
- 不修改 `.venv`、`node_modules` 等依赖目录；不把密钥、令牌写入代码或日志。
- 删除或覆盖用户文件前先读取原内容；没有十足把握时不要删除。
- 工具调用轮数有限（默认 5 轮），尽量合并相关命令：把多个搜索或检查合并成一条命令，避免浪费轮次。
- 修改 Python/Node 等项目文件时，改动需符合项目结构，不要破坏现有 RAG、Memory、Skill Router 等已有功能。

## 失败处理

- 命令失败：先看 stderr 最后若干行，不要原样重复重试同一条命令。
- 超时：拆小命令、减少输出量（如加 `-q`、`--max-count`、只取前 N 行）。
- 测试失败：先读失败用例的断言和 traceback，定位到具体代码行再修改。
- 报错信息不完整：主动补充上下文（打印类型、变量值、路径）后重新复现。

## 输出格式

- 分析类：结论 + 关键代码位置 + 依据。
- 修改类：改动文件 + 改动点 + 原因 + 验证结果。
- Bug 类：根因 + 触发条件 + 修复方式 + 验证结果。

## 完成标准

1. 已阅读并理解相关代码，能说清关键逻辑位置。
2. Bug 或需求已定位到具体代码位置，且有证据支撑。
3. 改动最小、符合项目风格，未影响无关功能。
4. 已运行测试或验证，并记录结果。
5. 最终回答包含文件路径、改动内容和验证结论。
