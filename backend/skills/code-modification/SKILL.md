# 代码修改 Skill（code-modification）

## 目标

以最小、可审计的改动解决问题：改哪里、为什么改、改完是否验证通过，都能被别人复现。

## 使用场景

- 修复缺陷：根据报错或日志定位根因并修复。
- 实现小功能：新增函数、接口、配置项、脚本。
- 局部重构：在不改变外部行为的前提下整理代码。
- 调整配置与依赖：改环境变量、参数、依赖声明。

## 执行环境约定

- 所有工具以 `backend/` 为项目根目录，例如 `read_file` 传 `graph/agent.py`。
- `write_file`、`edit_file` 不允许越出 backend；访问仓库根目录文件写成 `../README.md`。
- `terminal` 与 `python_repl` 的工作目录都是 backend。
- 当前环境为 Windows，`terminal` 默认执行 PowerShell 命令。
- 路径统一用正斜杠 `/`。

## 工作流程

### 1. 锁定范围与完成标准

1. 明确任务类型：修 Bug / 加功能 / 重构 / 改配置。
2. 明确完成标准：什么现象消失、什么行为出现、用什么验证。
3. 范围模糊时先做一次快速勘察，不要凭空假设文件位置。

### 2. 读代码，建立映射

1. 用 `grep` 定位入口：函数名、类名、路由、配置键、日志文案。
2. 用 `read_file` 精读目标文件，关注函数签名、返回值、异常处理、外部依赖。
3. 顺着调用链向上找调用方、向下找被调方，确认改动的影响半径。
4. 形成"问题 → 代码位置 → 修改点"的清单后再动手。

### 3. 小步修改

1. 改已有文件优先用 `edit_file`：`old_text` 必须从 `read_file` 结果逐字复制，并带足上下文保证唯一；多处匹配时用 `replace_all=true`。
2. 新建文件或整文件重写用 `write_file`；覆盖已有文件必须显式 `overwrite=true`，不要用 `terminal` 重定向绕过。
3. 一次只改一个逻辑点，改完立即自检。
4. 严格遵循项目现有风格：命名、缩进、注释语言、目录结构保持一致。
5. 只改与任务相关的代码，不重排、不删除无关逻辑，不顺手"优化"。

### 4. 自检

1. Python 语法检查：`terminal` 执行 `python -m py_compile <文件>`。
2. 导入检查：`python -c "import <模块>"`（在 backend 目录下）。
3. 用 `git_diff` 或 `read_file` 复查改动，确认没有误改。
4. 需要行为验证时，交给测试 Agent 或调用 `run_tests`。

### 5. 汇报

结论先行：改了什么、为什么改、验证结果如何；列出文件路径与关键改动点；未验证或有风险的部分明确说明。

## 工具使用约定

- `grep`：跨文件定位定义、引用、配置项、日志文案。
- `read_file`：精读单个文件，大文件先用 `grep` 定位再分段读。
- `edit_file`：精确替换已有文件内容，是改代码的首选。
- `write_file`：新建文件或整文件重写。
- `terminal`：语法检查、运行命令、查看目录。
- `python_repl`：验证小片段逻辑、做数据转换。
- `git_diff`：需要时查看改动差异，确认改动范围。

## 安全与边界

- 不在未确认根因前改代码；不改与任务无关的文件。
- 不删除用户已有功能；确需删除时要说明理由。
- 不执行破坏性命令（`rm -rf`、强制覆盖、`git reset --hard`）。
- 不提交、不推送：版本操作交给 Git 管理 Agent 或用户确认。
- 修改无法验证时，明确说明"未验证"及原因。
