# 测试执行 Skill（test-execution）

## 目标

用可复现的命令给出"通过还是失败、失败在哪、为什么失败"的确定结论，而不是"应该没问题"。

## 使用场景

- 运行项目既有测试套件，确认当前状态是否健康。
- 验证代码修改后行为是否正确、是否引入回归。
- 复现用户报告的 Bug，构造最小复现用例。
- 在改动前后跑同一组测试做对比。

## 执行环境约定

- 所有工具以 `backend/` 为项目根目录，`terminal`、`run_tests`、`python_repl` 都在该目录下执行。
- 当前环境为 Windows，`terminal` 默认执行 PowerShell 命令。
- 运行测试前先确认解释器/依赖是否可用，例如 `python --version`、`python -m pytest --version`。

## 工作流程

### 1. 先探明测试环境

1. 用 `grep` 或 `terminal` 查看项目测试框架与入口：`pytest.ini`、`pyproject.toml`、`package.json`、`go.mod`、`Cargo.toml`，以及 `test_*.py` / `*_test.go` 等测试文件。
2. 确认依赖已安装；缺依赖时先说明，不要跳过。
3. 明确本次验证目标，选择最小相关测试范围，而不是一上来跑全量。

### 2. 运行测试

1. 优先用 `run_tests`：`framework=auto` 自动探测，`path` 限定测试文件或目录，`extra_args` 追加参数（如 `-k "关键字" -x -q`）。
2. 需要完全自定义命令时用 `run_tests(command=...)`。
3. 需要观察真实交互时用 `terminal` 手动执行，但要记录完整命令。
4. 记录退出码、通过/失败/错误/跳过数量。

### 3. 复现问题

1. 复现前先明确"期望行为"和"实际行为"。
2. 用最小输入隔离问题：缩小到单个函数、单个用例、单个参数。
3. 无法复现时，明确列出缺少的条件（数据、环境、时序、并发），不要假装复现成功。
4. 用 `python_repl` 快速验证单点假设，再用 `run_tests` 做正式回归。

### 4. 定位失败

1. 从失败输出中提取：用例名、断言差异、异常类型、堆栈顶部的业务代码行。
2. 用 `grep` + `read_file` 定位到被测代码，区分"测试写错"和"实现有 Bug"。
3. 区分"新引入的失败"和"本来就失败的用例"，必要时用 `git_diff` 确认改动范围。

### 5. 汇报

结论先行：通过/失败、失败数量与原因、是否为本次改动引入、建议下一步。

## 工具使用约定

- `run_tests`：运行测试并返回结构化结果，首选工具。
- `terminal`：环境探测、手动跑命令、查看版本。
- `grep` / `read_file`：定位测试与实现代码。
- `python_repl`：验证单点假设或构造最小复现。
- `git_diff`：确认改动范围，判断失败是否由本次改动引入。

## 安全与边界

- 不为了"让测试通过"而删除或跳过失败用例；确需跳过要说明原因。
- 不修改测试断言来迁就错误实现。
- 测试超时必须终止并如实报告，不要静默忽略。
- 未实际运行就不要声称"测试通过"；无法运行要说明原因。
