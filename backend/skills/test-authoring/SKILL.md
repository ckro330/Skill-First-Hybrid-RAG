# 测试编写 Skill（test-authoring）

## 目标

用最少的用例覆盖最值得保护的行为：把"这段代码该怎么表现"固化成可重复执行的断言。

## 使用场景

- 为新增/修改的函数补单元测试。
- 为已修复的 Bug 补回归用例，防止复发。
- 为核心逻辑的边界条件补测试（空值、越界、异常分支）。
- 提升模块覆盖率，优先补高风险路径。

## 执行环境约定

- 以 `backend/` 为项目根目录，新测试文件放在项目既有测试目录结构下。
- 路径统一用正斜杠 `/`；当前环境为 Windows，`terminal` 执行 PowerShell 命令。
- 必须先确认项目使用的测试框架（pytest / unittest / jest / vitest / go test 等），不要混用。

## 工作流程

### 1. 读懂被测对象

1. 用 `grep` 找到被测函数/类的定义与现有调用方。
2. 用 `read_file` 精读实现，明确：输入、输出、副作用、异常、边界。
3. 查看同目录已有测试文件，模仿其命名、断言库、fixture/夹具、运行方式。

### 2. 设计用例

优先覆盖以下顺序：

1. 正常路径（Happy path）。
2. 边界条件（空、0、最大值、越界、单元素）。
3. 异常分支（非法输入、依赖失败、超时）。
4. 回归点（本次修复对应的具体 Bug 场景）。

每个用例只验证一个行为，名称要能表达意图，例如 `test_parse_empty_log_returns_zero_stats`。

### 3. 编写测试

1. 用 `write_file` 新建测试文件；改动已有测试用 `edit_file`。
2. 测试数据尽量内联、最小、自解释，避免依赖外部网络或真实数据库。
3. 需要 mock/打桩时，只替换必要的外部依赖，不要 mock 掉被测逻辑本身。
4. 遵循项目现有风格与目录约定，不引入新的测试框架或重量级依赖。

### 4. 运行与修正

1. 用 `run_tests` 运行新测试（`path` 指向新文件），确认通过。
2. 测试失败时先判断是测试写错还是实现有问题；不要为了通过而放宽断言。
3. 确认新测试在实现被破坏时确实会失败（必要时做一次临时反向验证）。

### 5. 汇报

列出新增测试文件、覆盖的行为点、运行命令与结果。

## 工具使用约定

- `grep` / `read_file`：理解被测代码与既有测试风格。
- `write_file`：新建测试文件。
- `edit_file`：修改已有测试文件。
- `run_tests`：运行并验证测试。
- `python_repl`：验证测试数据构造或断言逻辑。

## 安全与边界

- 不修改被测实现来迁就测试；实现有问题应单独指出。
- 不删除、不弱化已有测试。
- 不写依赖真实外部服务、随机不可复现的测试用例。
- 未实际运行通过，不得宣称测试有效。
