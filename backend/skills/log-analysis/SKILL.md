# 日志分析 Skill（log-analysis）

## 目标

把一个"日志看起来有问题"的模糊诉求，收敛成"哪一行、什么错误、出现多少次、对应哪段代码、根因是什么"的可执行结论。

## 使用场景

- 排查运行报错、接口 500、任务失败、进程崩溃。
- 统计错误频次、错误类型分布、错误随时间的变化。
- 还原某个请求/任务在日志中的完整时间线。
- 从异常堆栈反推代码位置与触发条件。

## 执行环境约定

- 所有工具以 `backend/` 为项目根目录，相对路径基于该目录，例如 `storage/logs/app.log`。
- 访问仓库根目录文件时写成 `../README.md`；路径统一用正斜杠 `/`。
- 当前环境为 Windows，`terminal` 默认执行 PowerShell 命令，不要依赖 bash 专有语法。
- 日志文件可能很大：默认不要用 `read_file` 整文件读取，先用 `log_stats` / `log_search` 缩小范围。

## 工作流程

### 1. 先看全局，不急着下钻

1. 确认日志文件路径。路径不明时先用 `terminal` 或 `grep` 定位，例如 `rg --files`、`Get-ChildItem -Recurse -Filter *.log`。
2. 用 `log_stats` 统计总行数、级别分布和 Top 错误指纹，先判断"是否真的异常"以及"主要问题类型"。
3. 记录基线：正常时各类级别的量级，避免把正常告警当成故障。

### 2. 过滤定位

1. 用 `log_search` 按 `level=ERROR/FATAL` 过滤，必要时空格配合 `pattern` 正则缩小到具体接口、请求 ID、模块名。
2. 命中过多时，逐步加条件：先加级别，再加关键字，再加时间窗（用 pattern 匹配时间戳前缀）。
3. 命中过少时，先去掉大小写限制，或改用同义词/错误码原词重试。
4. 大文件用 `tail_lines` 只看最近一段，避免把历史噪声当成当前故障。

### 3. 还原时间线与堆栈

1. 对关键错误，用 `log_search` 的 `context_lines` 取前后文，确认完整异常堆栈与触发参数。
2. 找到请求/任务 ID 后，用它作为 pattern 拉出该 ID 的完整生命周期。
3. 堆栈中的类名、函数名、文件行号要逐条记录，作为下一步代码关联的输入。

### 4. 关联代码

1. 用 `grep` 在代码仓库中搜索堆栈里的关键函数名、日志文案、错误码，定位到具体文件与行号。
2. 需要理解上下文时用 `read_file` 精读该处代码，必要时用 `terminal` 查看调用方。
3. 用 `python_repl` 做日志聚合：按小时/按接口统计错误数、计算错误率、归并同类堆栈。

### 5. 给出结论

结论先行：**是什么错、在哪、多严重、根因指向哪段代码、建议怎么改**。

## 工具使用约定

- `log_stats`：第一步，看整体分布与 Top 错误指纹，不修改文件。
- `log_search`：按级别/正则定位命中行，带行号与上下文；大文件配 `tail_lines`。
- `grep`：跨文件搜索代码中的函数名、日志文案、错误码。
- `read_file`：精读命中的代码片段，不要整文件读取大文件。
- `python_repl`：做计数、分组、排序等聚合分析。
- `terminal`：定位日志文件、查看文件大小与目录结构。

## 输出格式

- 结论：一句话说明问题与根因方向。
- 证据：`文件:行号` + 关键日志原文（截断到必要长度）。
- 统计：错误次数、影响范围、时间分布。
- 关联：涉及的代码文件与函数。
- 未确认项：无法从日志确定的部分要明确说明，不要臆测。

## 安全与边界

- 只读分析为主，不要为了"清理日志"而删除或覆盖日志文件。
- 不要把日志里的密钥、令牌、个人隐私原样大段复述。
- 无法确定根因时，明确列出还需要哪些信息（更早的日志、复现步骤、配置）。
